# Критерии наполнения слайдов (outline → HTML)

Этот файл — контракт **объёма и структуры** для `outline.md`.
Он отвечает на вопрос: *сколько и какой информации писать в план, чтобы
слайд заполнялся ровно, без пустоты и без переполнения*.

Связка документов:

| Файл | Роль |
|---|---|
| `OUTLINE_CRITERIA.md` (этот файл) | Сколько писать и в каких полях |
| [`DENSITY.md`](DENSITY.md) | Шпаргалка «антипустые слайды» |
| `outline.example.md` | Формат записи плана |
| `TEMPLATE.md` | Как превращать план в HTML и какой layout брать |

Режим плотности: **reading-first**. Слайд должен быть понятен без устного доклада.

---

## 0. Правило плотности (обязательно)

Цель визуала: контентный слайд занимает **~80–100%** полезной площади карточки.
`hero` — исключение (титул может быть просторным).

| Правило | Действие |
|---|---|
| Писать бюджет | Ближе к **верхней** границе оптимума/максимума типа, не к нижней |
| Мало интересного контента | **Объединять** слайды, а не оставлять полупустой |
| Переполнение | Разделять слайды или менять layout — не уменьшать шрифт |
| Один тезис | На слайде один **главный тезис**; несколько **компонентов** того же тезиса (duo + callout, facts + QR + выводы, pipeline + SVG + легенда) — норма |
| Два независимых тезиса | Два слайда (или явный merge в один новый тезис) |

В outline рекомендуется блок `# Замечания по плотности` (таблица «было → стало → почему») —
как журнал merge и мест под особым контролем при генерации HTML.

Краткая шпаргалка симптомов и действий: [`DENSITY.md`](DENSITY.md).

---

## 0.1. Общие лимиты (для любого слайда)

| Поле | Оптимум | Максимум | Если больше |
|---|---|---|---|
| Заголовок слайда (`## Слайд N — …` / `section-title`) | 3–6 слов | 8 слов | Сократить; смысл вынести в lead |
| `Главный тезис` | 1 фраза, 8–16 слов | 20 слов | Разбить на тезис + lead |
| `section-lead` / вводный тезис | 1 предложение, 12–22 слова | 2 предложения / ~40 слов | Лишнее → callout или следующий слайд |
| Короткое имя в TOC | 2–5 слов | 6 слов | Обрезать без потери смысла |
| Главных тезисов на слайде | 1 | 1 | Разделить **или** объединить в новый общий тезис |

**Каталог презентации:** `docs/presentations/<slug>/`, где `<slug>` =
`[a-z0-9]+(-[a-z0-9]+)*` (например `gradle`, `mcp-server`). Имя каталога —
стабильный сегмент URL в Dokka; не переименовывать без необходимости.

**Правило разбиения:** если для одного `## Слайд` нужно превысить лимит layout —
в плане сразу делать два слайда, а не «впихнуть позже».

**Правило объединения:** если после разбиения или с нуля слайд остаётся «жидким»
(3 коротких буллета, pipeline из одних ярлыков, comparison без нижнего блока) —
смержить со смежным слайдом того же раздела и описать merge в `# Замечания по плотности`.

**Пометки, которые не выводятся на слайд:**

- `Визуал:` — указание композиции;
- `Интерактивность:` — поведение;
- `Обязательные факты:` — нельзя терять при сжатии, но формулировку можно уплотнить.

---

## 0.2. Длина презентации

| Ориентир | Когда |
|---|---|
| 5–12 слайдов | Узкая тема, один контур |
| 10–20 слайдов | Смесь обзора и практики репозитория (типичный Guides) |
| до ~25 | Ок, если каждый слайд плотный; резать воздух и дубли, не смысл |

Не цель — уложиться в короткий счётчик. Цель — плотные, интересные слайды без
полупустых экранов.

---

## 0.3. Допустимые комбинации layout (один тезис)

Явно разрешено на одном слайде (часто с `deck--fill`):

| Комбинация | Зачем |
|---|---|
| `comparison` + callout/checklist «когда выбирать» | Иначе duo часто заполняет ~30% площади |
| `facts` + `.qr-card` + список выводов | Популярность / история / ссылки |
| `pipeline` + `diagram` + легенда | Lifecycle + граф |
| `facts` + `rule` | Кэши + контракт configuration time |
| `comparison` / duo из двух плотных списков | Команды \| правила |
| `cards-2x2` + callout | Итог / conventions |
| `code` + пояснения + вторичный список | Пример + «ещё в проекте» |

Запрещено без нового тезиса: длинный код + другая независимая тема; два
равноправных comparison на одном экране.

---

## 1. Как заполнять блок `## Слайд`

Минимальный каркас каждого слайда в outline:

```markdown
## Слайд N — Короткий заголовок

Тип: <layout>

Главный тезис: <одна фраза>

Содержание:
- …
```

Допустимые значения `Тип:`:

| Тип в outline | Layout в TEMPLATE |
|---|---|
| `hero` | Title / hero |
| `content` | Обычный content slide |
| `cards-2x2` | Карточки 2×2 |
| `comparison` | Две колонки (`.duo-grid`) |
| `facts` | Факты и метрики (`.fact-grid`) |
| `pipeline` | Последовательность |
| `code` | Код |
| `callout` | Важный вывод (часто вместе с другим layout) |
| `checklist` | Чеклист |
| `rule` | Правило или контракт |
| `diagram` | Диаграмма |

Ниже — бюджет контента **на один слайд** выбранного типа.
Для плотности предпочитать верхнюю границу; нижняя — только если слайд потом
смержат или это осознанно короткий акцент.

## 2. Бюджеты по типам слайдов

### 2.1. `hero` — титульный

Использовать **ровно один раз**, первым слайдом.

| Поле | Оптимум | Максимум | Примечание |
|---|---|---|---|
| eyebrow (контекст · версия/дата) | 3–7 слов | 10 слов | Одна строка |
| brand / короткое название | 2–5 слов | 6 слов | Герой-сигнал бренда/темы |
| главный тезис (`hero__title`) | 8–14 слов | 18 слов | Одна сильная фраза |
| lead (ценность) | 1 предложение, 15–28 слов | 2 предложения / ~40 слов | Без списка и без кода |

**Содержание в outline — 3–4 пункта максимум**, по одному на поле выше.
Не добавлять карточки, метрики, чеклисты на hero.

Слишком мало: только название без тезиса и lead.
Слишком много: любой второй смысловой блок → вынести на слайд 2.

---

### 2.2. `content` — обычный смысловой слайд

| Поле | Оптимум | Максимум |
|---|---|---|
| Заголовок | 3–6 слов | 8 слов |
| Lead | 1 предложение | 2 предложения |
| Список пунктов | 4–6 | 7 |
| Длина пункта | 6–14 слов | 20 слов |
| Callout (опционально) | 1 фраза / 12–25 слов | 1 блок |

После lead — один **тезисный** контур. Допустим lead + список + callout, если
все три усиливают тот же тезис. Не комбинировать длинный список + код + чужую
диаграмму на одном content-слайде.

---

### 2.3. `cards-2x2` — четыре равноправные идеи

| Поле | Оптимум | Максимум |
|---|---|---|
| Число карточек | 4 | 4 для 2×2; иначе 2 или максимум 6 на отдельном grid-слайде |
| Kicker на карточку | 1–3 слова | 4 слова |
| Заголовок карточки | 2–5 слов | 7 слов |
| Текст карточки | абзац 10–22 слова **и/или** список 2–5 пунктов | абзац ≤ 28 слов; до 5 пунктов по 4–14 слов |
| Lead слайда | 1 предложение | 2 предложения |

Норма плотности: `.method-card__text` + `.method-card__list` (2–5 буллетов),
а не одно короткое предложение на всю карточку.

В outline на каждую карточку — отдельный пункт с явной структурой:

```markdown
Содержание:
1. Kicker: …; Title: …; Text: …;
   Буллеты: …; …; …
2. …
```

Слишком мало: карточка только с заголовком или одним предложением без буллетов
при пустом низе слайда → добить текст или смержить темы.
Слишком много: >5 пунктов внутри карточки или 5-я равноправная идея → новый слайд
или вынести в callout.

---

### 2.4. `comparison` — две колонки

| Поле | Оптимум | Максимум |
|---|---|---|
| Колонок | 2 | 2 |
| Название подхода | 1–4 слова | 6 слов |
| Пунктов в колонке | 4–5 | 8 (для dense duo вроде «команды \| правила») |
| Длина пункта | 5–14 слов | 20 слов |
| Плотность сторон | Сопоставимая | Разница не больше ±1 пункта |
| Нижний блок | callout / «когда выбирать» | 1 блок, обязателен если колонки короткие |

В outline обязательно два симметричных блока + при необходимости низ:

```markdown
Левая колонка:
- название;
- пункт;
…

Правая колонка:
- название;
- пункт;
…

Нижний блок «Когда выбирать» / callout:
- …
```

Не смешивать comparison с длинным кодом: код → отдельный `code`-слайд.

---

### 2.5. `facts` — факты и метрики

| Поле | Оптимум | Максимум |
|---|---|---|
| Число фактов | 4–5 | 6 |
| `label` | 1–3 слова | 5 слов |
| `value` | короткое значение (число, версия, имя) | одна строка ≤ 6–8 слов |
| `note` | 1–2 предложения / 12–28 слов | ~40 слов (2–3 коротких предложения) |
| Lead | 1 предложение | 2 предложения |

Каждый факт в outline:

```markdown
Содержание:
- Label: Value — развёрнутая note (зачем метрика / как читать)
```

Если плашка иначе пустая — удлинять `note`, а не плодить пустые facts.
Допустимы facts + QR + список выводов на одном слайде (один тезис «популярность /
контекст»).

---

### 2.6. `pipeline` — последовательность

| Поле | Оптимум | Максимум |
|---|---|---|
| Число шагов | 3–5 | 6 |
| Текст шага | 2–5 слов или «ярлык · пояснение» | 8 слов |
| Lead | 1 предложение | 2 предложения |
| Итоговый callout / легенда | 1 блок | обязателен, если шаги короткие |

Если шагов > 6 — в outline сразу два pipeline-слайда (часть 1 / часть 2).
Частый плотный паттерн: pipeline + diagram + список фактов.

```markdown
Содержание:
1. Init · settings, Wrapper
2. Configure · проекты и задачи
3. Execute · устаревшие узлы
4. Result · артефакты

Визуал: pipeline + SVG графа + легенда.
```

---

### 2.7. `code` — технический пример

| Поле | Оптимум | Максимум |
|---|---|---|
| Строк кода (видимых) | 6–10 | 12–14 |
| Пояснений под кодом | 3–5 | 7 (если есть блок «ещё в проекте») |
| Длина пояснения | 6–16 слов | 22 слова |
| Lead | 1 предложение: *что доказывает пример* | 2 предложения |

Код в outline — **только** fenced block; сохраняется дословно.

Слишком мало: код без тезиса и без 2+ пояснений.
Слишком много: >14 строк или второй блок кода → продолжение на следующем слайде.
Вторичный список («ещё conventions / ещё команды») после пояснений — ок.

---

### 2.8. `checklist` — рекомендации / следующие шаги

| Поле | Оптимум | Максимум |
|---|---|---|
| Пунктов | 5–7 | 7 |
| Длина пункта | 6–14 слов | 18 слов |
| Финальный вывод / callout | 1 фраза, 10–20 слов | 25 слов |
| Lead | 1 предложение | 2 предложения |

Пункты — действия (глагол в начале), не рассуждения.
Два чеклиста рядом лучше оформить как `comparison` / duo, а не два слайда
с пустотой.

---

### 2.9. `rule` — правило / контракт

| Поле | Оптимум | Максимум |
|---|---|---|
| Имя правила | 2–6 слов | 8 слов |
| Because (почему) | 1 предложение, 12–22 слова | 30 слов |
| Human (простыми словами) | 1 предложение, 10–20 слов | 28 слов |
| Flow (допустимо / запрещено) | 2 коротких ветки | 2 ветки по ≤ 8 слов |
| Пример в `<details>` | 4–8 строк кода или 2–3 пункта | 12 строк |
| Lead слайда | 1 предложение | 2 предложения |

На слайде — **одно** правило. Второе правило = новый слайд.
Часто комбинируют с `facts` про те же флаги/кэши.

---

### 2.10. `diagram` — диаграмма

| Поле | Оптимум | Максимум |
|---|---|---|
| Узлов на схеме | 4–7 | 9 |
| Подпись узла | 1–3 слова; длинные — **две строки** (`tspan`) | не одна длинная строка в узком rect |
| Размер узла | компактный (~64–120×36–44) | не раздувать «чтобы заполнить» |
| Связей (стрелок) | 3–6 | 8 |
| Обязательные факты / легенда | 4–5 пунктов | 5 пунктов |
| Lead | 1 предложение: *что показывает схема* | 2 предложения |

**SVG-контракт (обязателен):**

- стрелки заканчиваются на **гранях** узлов, не в пустоте;
- после правок — визуальная проверка в браузере;
- длинные имена (`settings/configure`, `compileKotlin`) — две строки внутри узла;
- под схемой — легенда + факты; сам SVG без легенды часто оставляет низ пустым.

```markdown
Визуал: узлы A → B → C; ветка B → D вниз; узлы компактные; длинные подписи в 2 строки.
Обязательные факты:
- …
```

Если узлов > 9 — разбить на overview + detail.

---

### 2.11. `callout` — акцент вывода

Обычно **не отдельный слайд**, а завершающий блок на `content` / `pipeline` /
`checklist` / `comparison` / `cards-2x2`.

| Поле | Оптимум | Максимум |
|---|---|---|
| Callout на слайде | 1 | 1 |
| Длина | 12–25 слов | 35 слов |
| `callout--cyan` | для ключевого вывода раздела | не чаще 1 раза на 2–3 слайда |

---

### 2.12. Типовые merge (когда слайды жидкие)

| Было по отдельности | Стало | Почему |
|---|---|---|
| Wrapper + Daemon (+ «что такое X») | cards-2x2 «модель и запуск» | по 3–4 коротких пункта |
| Lifecycle + граф задач | pipeline + diagram + легенда | pipeline из ярлыков пустой |
| Configuration Cache + Build Cache | facts + rule | одна тема скорости |
| Команды + CI + правила | comparison duo | два чеклиста лучше рядом |
| Takeaways + «дальше» | cards + callout next | два коротких финала |
| Pros + cons + comparison | один comparison + «когда выбирать» | три жидких слайда |

## 3. Метаданные outline (front matter)

| Поле | Оптимум | Зачем |
|---|---|---|
| `title` | 2–6 слов | `<title>`, brand, TOC |
| `subtitle` | 6–14 слов | главный тезис hero / meta description |
| `author` | имя | опционально в контексте |
| `date` / версия | коротко | eyebrow |
| `language` | `ru` по умолчанию | язык UI-текстов |
| `audience` | 3–8 слов | тон формулировок, не текст на слайде |
| `guides` | `true` по умолчанию; `false` — черновик | скрыть из вкладки Guides в Dokka |

Пока идёт итерация outline/HTML — держать `guides: false`; включать в Guides
только после визуального ревью.

`# Общий замысел` — **1 абзац, 2–4 предложения**. Не копировать его дословно на слайды;
это ориентир для выбора акцентов.

`# Замечания по плотности` — опционально, но рекомендуется для нетривиальных deck.

`# Дополнительные материалы` — без лимита; на слайды не попадает, пока не перенесено
в конкретный `## Слайд`.

---

## 4. Чеклист автора плана (перед передачей модели)

Для каждого `## Слайд` проверить:

1. Указан ровно один `Тип:` из таблицы выше (комбинации — через `Визуал:`).
2. Есть `Главный тезис` в пределах лимита.
3. Число пунктов/карточек/шагов/строк кода ≤ максимума типа; плотность ближе к верху.
4. Нет второго независимого тезиса на том же слайде.
5. Слайд не выглядит заведомо полупустым (см. [`DENSITY.md`](DENSITY.md)).
6. `Визуал:` / `Интерактивность:` не дублируют текст, который должен быть на слайде.
7. Код, который нельзя перефразировать, лежит в fenced block.
8. Факты под `Обязательные факты:` сформулированы коротко и проверяемо.
9. Для `diagram`: компактные узлы, стрелки к граням, легенда под схемой.

Для всего плана:

1. Первый слайд — `hero`, и он один.
2. Длина согласована с замыслом (часто 10–20; до ~25 при плотности).
3. Смежные слайды не повторяют один и тот же список другими словами.
4. Comparison / cards / facts имеют равномерную плотность элементов.
5. Жидкие слайды смержены; merge отражены в `# Замечания по плотности`.
6. Черновик: `guides: false`, пока HTML не стабилен.

## 5. Быстрая шпаргалка «сколько писать»

| Тип | Главный объём (целиться сюда) |
|---|---|
| `hero` | 4 поля: eyebrow, brand, тезис, lead |
| `content` | lead + 4–6 пунктов (+ callout) |
| `cards-2x2` | 4 × (kicker + title + абзац + 2–5 буллетов) |
| `comparison` | 2 × 4–5 пунктов + нижний callout при необходимости |
| `facts` | 4–5 метрик с развёрнутой note |
| `pipeline` | 3–5 шагов с пояснением + легенда/callout |
| `code` | 6–12 строк + 3–5 пояснений |
| `checklist` | 5–7 действий + финальная фраза |
| `rule` | имя + because + human + 2 ветки flow |
| `diagram` | 4–7 компактных узлов + 4–5 фактов-легенды |

Если сомневаетесь между «коротко» и «плотно» для reading-first Guides —
пишите **плотнее** (верх бюджета). Пустой низ карточки хуже, чем полный слайд.
Переполнение модель должна резать или дробить; обязательные факты не терять.
