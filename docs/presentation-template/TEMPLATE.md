# Ru BizGen Presentation Template

Этот файл — обязательный контракт генерации новых презентаций. Его правила имеют
приоритет над стилистическими решениями модели. Меняется содержание, но не
визуальная система, навигация и общий подход.

## 1. Эталон

- Визуальные эталоны:
  - `docs/presentations/archunit/index.html` — составные слайды, QR, rule, graph;
  - `docs/presentations/gradle/index.html` — плотность, duo, dense cards, pipeline+SVG, facts+rule.
- Общие стили: `docs/presentation-template/styles.css`.
- Общая навигация: `docs/presentation-template/app.js`.
- Язык презентации берётся из входного плана; по умолчанию — русский.
- Режим плотности: reading-first. Слайд должен быть понятен без устного доклада.
- Бюджеты и антипустые правила: `OUTLINE_CRITERIA.md`, шпаргалка `DENSITY.md`.

## 2. Неизменяемая дизайн-система

### Палитра

Использовать только CSS-переменные из `styles.css`:

- основной фон `--bg: #e6eaf5`;
- карточки `--bg-elevated: #ffffff`;
- вторичные панели `--bg-panel: #f7f8fc`;
- основной текст `--ink: #262c40`;
- вторичный текст `--ink-muted: #5c6578`;
- акцент `--blue: #476bf0`;
- успех `--ok: #1f9d63`;
- ошибка `--danger: #e03b4c`.

Не вводить новые акцентные цвета, градиентные темы или тёмный режим.

### Типографика

- Основной шрифт: Montserrat, веса 400–700.
- Код и технические подписи: IBM Plex Mono, веса 400–600.
- Заголовки короткие, полужирные, с плотным межбуквенным интервалом.
- Технические идентификаторы, команды, пути и API оформлять через `<code>`.

### Геометрия

- Светлая карточка презентации на мягком градиентном фоне.
- Левое оглавление шириной `280px`.
- Основной радиус карточек `14px`, оболочки `24px`.
- Тонкая серая рамка, мягкая синяя тень.
- Контентная направляющая до `1440px`.
- Воздух — между блоками и для выравнивания; контентная карточка слайда
  не должна быть полупустой. Для смысловых слайдов предпочитать `deck--fill`.
  `hero` может оставаться просторным.

## 3. Обязательный HTML-каркас

Новая презентация должна сохранять:

- `.progress`;
- `.layout`;
- `.toc` с брендом, подзаголовком и ссылкой на каждый слайд;
- `.main`, `.deck-chrome`, `.slide-counter`, кнопки назад/вперёд;
- `.card-shell`;
- один `<section class="deck">` на слайд;
- уникальный `id` у каждого слайда;
- `is-active` только у первого слайда;
- подключение общих `styles.css` и `app.js`.

Порядок ссылок в оглавлении обязан совпадать с порядком `<section>`.
Нумерация формируется двумя цифрами: `01`, `02`, ….

## 4. Библиотека слайдов

Модель выбирает минимально достаточный layout под смысл, а не повторяет один и
тот же grid на каждом слайде.

### Title / hero

Использовать один раз в начале:

```html
<section class="deck hero is-active" id="intro">
  <div class="hero__glow" aria-hidden="true"></div>
  <p class="hero__eyebrow">Контекст · версия или дата</p>
  <h1 class="hero__brand">Короткое название</h1>
  <p class="hero__title">Главный тезис презентации</p>
  <p class="hero__lead">Одно компактное объяснение ценности.</p>
</section>
```

### Обычный content slide

```html
<section class="deck" id="topic">
  <h2 class="section-title">Заголовок</h2>
  <p class="section-lead">Один вводный тезис.</p>
  <!-- Смысловой блок: список, код, callout или схема -->
</section>
```

### Карточки 2×2

Для четырёх равноправных идей использовать
`.deck.deck--fill > .method-grid.method-grid--2x2` и `.method-card`.
У каждой карточки: kicker, заголовок, `.method-card__text` и при плотности
`.method-card__list` (2–5 пунктов). Одно короткое предложение без списка —
обычно слишком жидко.

### Две колонки

Для сравнения двух подходов использовать `.duo-grid` и `.duo-card`.
Обе стороны должны иметь сопоставимую информационную плотность.
Если колонки короткие — добавить нижний callout / блок «когда выбирать»
(не оставлять нижнюю половину пустой).

### Факты и метрики

Для 2–6 фактов использовать `.fact-grid`, `.fact`,
`.fact__label`, `.fact__value`, `.fact__note`.
`fact__note` может быть 1–2 предложениями, если иначе плашка пустая.
Частый паттерн: facts + `.qr-card` + список выводов.

### QR-карточка

Для ссылки на внешний ресурс (официальный сайт, GitHub) использовать
`.qr-card`, `.qr-card__img`, `.qr-card__title`, `.qr-card__url`.
PNG генерировать скриптом `utils/qr/generate_qr.py` (см. README); файл рядом с `index.html`.

### Последовательность

Для короткого процесса использовать `.pipeline`, `.pipeline__step`,
`.pipeline__arrow`. Если этапов больше шести, разбить материал на два слайда.

### Код

Использовать `<pre class="code" data-highlight>`. Не вставлять более 12–14
видимых строк кода на один слайд. Сохранять реальные переносы и отступы.

### Важный вывод

Использовать `.callout`; для особенно важного синего акцента —
`.callout.callout--cyan`. На слайде обычно не более одного callout.

### Чеклист

Для последовательных рекомендаций использовать `<ol class="checklist">`.
Оптимально 4–7 пунктов.

### Правило или контракт

Для тезиса с объяснением, кодом, допустимым/запрещённым потоком и раскрываемым
примером использовать `.rule`, `.rule__name`, `.rule__because`,
`.rule__human`, `.rule__flow`, `.badge`, `<details class="break">`.

### Диаграмма

Предпочитать inline SVG в `.graph`. Использовать цвета из CSS-переменных,
тонкие линии, простые прямоугольные узлы и подписи IBM Plex Mono.
Диаграмма обязана иметь `role="img"` и понятный `aria-label`.

Обязательно:

- узлы компактные; длинные подписи — две строки (`<tspan>`);
- стрелки заканчиваются на гранях узлов, не в пустоте;
- под схемой — легенда и/или список фактов;
- после правок SVG — визуальная проверка в браузере.

## 5. Правила композиции

- Один слайд — один главный тезис (несколько компонентов того же тезиса — норма).
- Заголовок: до 8 слов.
- `section-lead`: 1–2 предложения.
- В обычном списке: 3–7 пунктов.
- В grid: максимум 6 карточек; предпочтительно 2 или 4.
- Контентные слайды: `class="deck deck--fill"`; не оставлять «лысую» нижнюю половину.
- Не уменьшать шрифт ради переполненного слайда — разделить слайд.
- Не использовать вертикальный скролл как штатный способ разместить слишком
  большой объём. Он допустим только как страховка существующего движка.
- Не создавать новый CSS-класс, если смысл выражается существующим компонентом.
- Новые layout-классы допустимы только для предметной диаграммы, которой нет в
  библиотеке, и должны использовать существующие tokens.
- При нехватке контента на плотный слайд — предложить merge в outline
  (см. `OUTLINE_CRITERIA.md` / `DENSITY.md`), а не генерировать полупустой HTML.

## 6. Интерактивность

`app.js` автоматически обеспечивает:

- переходы по оглавлению;
- кнопки назад/вперёд;
- клавиши `←`, `→`, `J`, `K`;
- swipe на touch-устройствах;
- hash-навигацию;
- progress bar и счётчик;
- подсветку Kotlin-подобного кода с `data-highlight`.

Предметную интерактивность добавлять только когда она помогает понять материал.
Она должна быть локальной, доступной с клавиатуры и не ломать базовую навигацию.

## 7. Работа с входным Markdown

Объём и структура пунктов плана задаются в `OUTLINE_CRITERIA.md`.
Этот раздел описывает только преобразование плана в HTML.

Для каждого раздела `## Слайд` во входном плане:

1. Выделить главный тезис.
2. Выбрать один layout из библиотеки.
3. Сжать повторы, но не удалять факты, помеченные как обязательные.
4. Сохранить код дословно, если он помечен fenced code block.
5. Использовать заметку `Визуал:` как указание на композицию, а не как текст.
6. Использовать заметку `Интерактивность:` как поведение, а не как текст.
7. Добавить ссылку в оглавление.

Модель может разделить один перегруженный пункт плана на несколько слайдов.
Объединять разные тезисы без причины нельзя; объединять **жидкие** слайды
одного раздела по указанию outline / `DENSITY.md` — нужно.

## 8. Критерии готовности

Перед завершением проверить:

- все ссылки оглавления ведут на существующие уникальные `id`;
- количество ссылок равно количеству `.deck`;
- первый слайд единственный содержит `is-active`;
- заголовок страницы и meta description соответствуют теме;
- нет текста чужой темы (ArchUnit/Gradle и т.п.), оставшегося из эталона;
- нет новых цветов, шрифтов, радиусов и теней;
- код не выходит за карточки;
- панели не перекрываются на desktop и mobile;
- кнопки, клавиатура, swipe и hash-навигация работают;
- `prefers-reduced-motion` сохранён;
- у изображений и SVG есть доступные описания;
- контентные слайды визуально заполнены (~80–100%); нет пустой нижней половины;
- SVG: нет стрелок в пустоту; текст не вылезает из узлов;
- QR (если есть): путь к PNG верный, alt/title/ссылка согласованы.

## 9. Публикация в Dokka

Генерация HTML заканчивается файлом `docs/presentations/<slug>/index.html`.
Публикация на GitHub Pages через Dokka — универсальный процесс: презентация
попадает во вкладку **Guides** автоматически, без hub-страницы и без правок
меню на каждую тему.

Полный контракт: [`PUBLISH_DOKKA.md`](PUBLISH_DOKKA.md).

Кратко после генерации HTML:

1. Презентация в `docs/presentations/<slug>/` с
   `../../presentation-template/{styles.css,app.js}`.
2. Не править `header.ftl` / footer под одну тему — сработает
   `generatePresentationsGuides` → `guides.json`.
3. Черновик можно скрыть из Guides: `guides: false` в front matter `outline.md`.
4. Локально: `./gradlew dokkaGenerateHtml`, проверить Guides в шапке Dokka.
5. Деплой: push/merge в `main`/`dev` → `docs.yml`.
