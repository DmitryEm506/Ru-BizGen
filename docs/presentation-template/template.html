Сравнение двух подходов

Равноплотные колонки + блок «когда выбирать», иначе низ слайда пустеет.

Подход A

Вариант слева

  • модель: краткое описание механики;
  • плюсы: скорость / гибкость / масштаб;
  • минусы: онбординг / churn / сложность;
  • где силён: типичный кейс A;
  • ещё один сопоставимый пункт.

Подход B

Вариант справа

  • модель: краткое описание механики;
  • плюсы: предсказуемость / дефолт / найм;
  • минусы: verbosity / кастомизация;
  • где силён: типичный кейс B;
  • ещё один сопоставимый пункт.
Когда выбирать. Бери A, если нужны гибкость и multi-module. Бери B, если важнее дефолт и совпадение с вакансиями. Общее: не спорьте хайпом — смотрите модель и стоимость поддержки.

Четыре опоры темы

В каждой карточке: kicker, title, абзац и список — не одно короткое предложение.

Модель

Главная идея №1

Короткий абзац: что это и почему важно. Можно с расшифровкой термина.

  • буллет с деталью A
  • буллет с деталью B
  • буллет с командой / API

Артефакты

Главная идея №2

Расшифруйте аббревиатуры (как GAV: Group / Artifact / Version).

  • G — …
  • A — …
  • V — …

Запуск

Главная идея №3

Контракт повторяемости: что фиксируется в репозитории.

  • всегда один входной скрипт / wrapper
  • обновление — осознанный diff
  • CI и локаль совпадают

Скорость

Главная идея №4

Долгоживущий процесс / кэш: что переиспользуется между запусками.

  • первая итерация дороже (прогрев)
  • при сбоях — явный reset / stop
  • в CI — границы шаринга
Callout под сеткой: единый контракт для всех модулей / потребителей.

Процесс и граф

Pipeline с пояснениями + компактный SVG: стрелки к граням, длинные подписи в две строки.

Init · подготовка → Configure · структура → Execute · работа → Result · артефакты
dependsOn / implicit ветка jar после compile
  • рёбра заканчиваются на гранях узлов — не в пустоте;
  • длинные имена — две строки (tspan), узлы компактные;
  • легенда + факты под схемой закрывают нижнюю половину слайда.

Метрики и правило

Плотные fact-плашки + один .rule того же тезиса (скорость / контракт).

Флаг A true Что кэшируется / ускоряется. Зачем на multi-project. Ключ в конфиге: org.example.a=true.
Флаг B true Другой уровень кэша (не путать с A). Локально и опционально между агентами.
Parallel true Независимые узлы графа / модули бегут параллельно. Выигрыш растёт с числом модулей.
JVM -Xmx4g Запас heap под тяжёлые задачи (docs, plugin, тесты).

Configuration Cache first

На multi-project фаза Configure часто дороже полезной работы Execute.

Не читайте окружение «как попало» на configuration time без declaration.

сериализуемая конфигурация скрытые side effects
Пример из репозитория 
org.gradle.configuration-cache=true
org.gradle.caching=true
org.gradle.parallel=true
Оба механизма дополняют друг друга — не заменяют.

Карта модулей

Root сверху, модули рядом, shared-logic снизу; solid / dashed в легенде.

include(…) includeBuild → conventions
  • узлы ~88×36 / 120×36 — стрелки читаются лучше;
  • solid и dashed несут разный смысл (легенда обязательна);
  • факты под схемой: что нельзя потерять при сжатии текста;
  • viewBox с запасом снизу — нижний узел не обрезается.

Технический пример

Код доказывает тезис; ниже — пояснения и блок «ещё в проекте». 

plugins {
  id("org.jetbrains.kotlin.jvm")
}

val libs = extensions.getByType<VersionCatalogsExtension>().named("libs")

kotlin {
  jvmToolchain(libs.findVersion("java").get().requiredVersion.toInt())
}
  • модулям не нужно дублировать toolchain локально;
  • версия JDK — из version catalog (java = "21");
  • подключение: id("ru-bizgen.kotlin-convention").
Ещё conventions в проекте.
  • testing-convention — JUnit Platform и теги дорогих тестов;
  • dokka-convention — HTML модуля и source links;
  • kover-convention — покрытие onCheck;
  • dokka-root-convention — Guides / sync презентаций.

Правило / контракт

Одно правило на слайд: имя, because, human, flow, опциональный details.

coreMustNotDependOnAdapters

«ядро не должно зависеть от адаптеров (plugin, mcp, perf)»

core остаётся переиспользуемым без знания об IDE и HTTP.

core → stdlib / свои пакеты core → plugin / mcp / perf
Пример проверки 
@ArchTest
val coreMustNotDependOnAdapters =
  noClasses().that().resideInAPackage("..core..")
    .should().dependOnClassesThat()
    .resideInAnyPackage("..plugin..", "..mcp..", "..perf..")

Команды и правила

Два чеклиста рядом лучше, чем два полупустых слайда.

Локаль · CI

Команды

  • ./gradlew check — быстрые проверки;
  • ./gradlew buildPlugin — артефакт плагина;
  • ./gradlew dokkaGenerateHtml — docs + Guides;
  • -PrunDistanceFinderTests — полный прогон;
  • -PrunIntegrationTests — UI integration;
  • push/PR CI — короткий feedback без тяжёлых тегов.

Контракт

Правила

  • версии только в catalog;
  • общая логика в conventions;
  • только Wrapper локально и в CI;
  • не отключать кэши без замера;
  • тяжёлые теги — явными флагами;
  • configuration time без скрытых side effects.
Тяжёлые наборы включайте явно — быстрый PR-check важнее полного прогона на каждый коммит.
