Gradle vs Maven

Одна экосистема артефактов — разная модель сборки; плюсы и цена выбора на одном экране.

Скорость · гибкость

Gradle

  • Модель: Kotlin DSL, DAG задач, инкрементальность по входам/выходам
  • Скорость: Configuration Cache, Build Cache, parallel из коробки
  • Гибкость: Task API и convention plugins без тяжёлого ритуала Maven plugin
  • Масштаб: multi-project, includeBuild, version catalog для крупных репо
  • Цена: круче онбординг, чаще churn major, сложнее отлаживать configuration

Дефолт · предсказуемость

Maven

  • Модель: декларативный pom.xml и фиксированный lifecycle фаз
  • Предсказуемость: один «стандарт индустрии», меньше сюрпризов между командами
  • Онбординг: проще найти людей и готовые корпоративные шаблоны
  • Экосистема: parent POM, profiles, огромный плагин-каталог
  • Цена: многословный XML и тяжелее выразить нестандартный граф задач
Когда выбирать. Бери Gradle — Android/Kotlin, кастомная сборка, multi-module + caches (кейс Ru BizGen). Бери Maven — классический Java-сервис, максимум предсказуемости и совпадения с вакансиями. Общее — Maven Central и GAV-координаты работают в обоих мирах. Не аргумент «только хайп»: смотри на модель сборки и стоимость поддержки скриптов.

Модель Gradle и запуск

Gradle — движок графа задач; Wrapper и Daemon делают запуск повторяемым и быстрым.

Модель

DAG, не «фаза Maven»

DAG (Directed Acyclic Graph) — ориентированный ациклический граф задач: узлы = tasks, рёбра = «сначала A, потом B». Циклов в графе быть не может.

  • Execute обходит подграф от запрошенной задачи (check, buildPlugin…)
  • рёбра — явный dependsOn и неявные от плагинов
  • входы/выходы решают up-to-date: неизменные узлы пропускаются
  • нет жёсткого набора фаз как у Maven — граф под ваш запрос
  • --dry-run печатает план без выполнения

Артефакты

Тот же Maven Central

Меняется движок сборки, не формат репозитория. GAV — координаты артефакта в Maven-мире.

  • Group — организация/namespace (org.jetbrains.kotlin)
  • Artifact — имя библиотеки (kotlin-stdlib)
  • Version — версия (2.4.0); вместе: group:name:version
  • в Gradle то же: implementation(…) / catalog libs.* → Central
  • миграция Maven→Gradle не требует «другого» репозитория артефактов

Wrapper

Версия в репозитории

gradlew + gradle/wrapper/ фиксируют дистрибутив — CI и ноутбуки совпадают.

  • всегда ./gradlew, не системный gradle
  • обновление Wrapper — осознанный diff
  • без локальной установки Gradle

Daemon

Тёплая JVM

Gradle Daemon — долгоживущий фоновый процесс: между запусками не поднимает JVM с нуля.

  • переиспользует JIT, классы плагинов и кэш метаданных
  • первая сборка после старта дороже (прогрев), дальше быстрее
  • ускоряет локальные итерации «поправил → ./gradlew check»
  • при сбоях/зависаниях: ./gradlew --stop и новый daemon
  • в CI — внутри одного job; между чистыми агентами не шарится
  • --no-daemon возможен, но для повседневной работы обычно не нужен
В Ru BizGen один Wrapper обслуживает core, plugin, mcp, perf и archunit — единый контракт команд.

Lifecycle и граф задач

Init → Configure → Execute строит DAG; up-to-date и кэш решают, что реально бежать.

Init · settings, included builds, Wrapper → Configure · проекты и задачи → Execute · устаревшие узлы → Result · артефакты и код выхода
dependsOn / implicit ветка jar после compileKotlin
  • рёбра — зависимости задач (dependsOn и неявные от плагинов);
  • up-to-date пропускает задачу с неизменными входами и выходами;
  • --dry-run показывает план без выполнения — удобно учить граф;
  • check — агрегатор проверок, не «магическая фаза» как у Maven;
  • Configuration Cache может пропустить повторный Configure, если входы стабильны.

Кэши и скорость

В Ru BizGen скорость сборки завязана на три флага и дисциплину configuration time.

Configuration Cache true Сериализует Configure на диск; при неизменных входах повтор чаще сразу в Execute. На multi-project — главный выигрыш: не пересчитывать все скрипты снова. Флаг: org.gradle.configuration-cache=true.
Build Cache true Кэширует выходы задач по ключу входов; hit → задача не пересчитывается. Локально и опционально между CI-агентами (remote cache). Флаг: org.gradle.caching=true — не путать с Configuration Cache.
Parallel true Независимые проекты/задачи без рёбер бегут на нескольких воркерах. Выигрыш растёт с числом модулей (core, plugin, mcp, perf, archunit). Флаг: org.gradle.parallel=true.
JVM -Xmx4g Запас heap/metaspace под IntelliJ Platform, Dokka, тесты и daemon. Без запаса CI/локаль ловят OOM на тяжёлой документации и plugin-задачах. Задано в org.gradle.jvmargs в gradle.properties.
Уровни CC ≠ BC Configuration Cache = фаза Configure (структура задач). Build Cache = артефакты Execute (outputs задач). Включайте оба: они дополняют друг друга, а не заменяют.

Configuration Cache first

На multi-project Configure часто дороже полезной работы Execute.

Не читайте окружение «как попало» на configuration time без declaration.

сериализуемая конфигурация скрытые side effects при configure
gradle.properties в Ru BizGen 
org.gradle.configuration-cache=true
org.gradle.caching=true
org.gradle.parallel=true
Все три флага уже включены в репозитории. Build Cache и Configuration Cache — разные механизмы.

Карта сборки Ru BizGen

Root включает пять модулей и composite build-logic с convention plugins.

include(…) includeBuild → conventions
  • settings.gradle.kts: includeBuild("build-logic") + пять include(...);
  • build-logic — composite build, не обычный subproject в include;
  • core без IntelliJ/Ktor; plugin и mcp переиспользуют generators;
  • perf — JMH; archunit — только архитектурные тесты в check;
  • смена convention в build-logic влияет на всех потребителей сразу.

Composite и conventions

Общая логика сборки живёт в build-logic и подключается как id("ru-bizgen.*-convention").

Composite

includeBuild

В settings.gradle.kts — includeBuild("build-logic"): отдельный Gradle-билд с convention plugins, которые модули подключают как обычные id(...).

  • явный аналог buildSrc без «магии» classpath корня
  • модули пишут id("ru-bizgen.*-convention"), без копипасты блоков
  • review «как собираем» = diff в build-logic/
  • смена convention сразу у всех потребителей

kotlin

kotlin-convention

Kotlin JVM + jvmToolchain 21 из version catalog — единый JDK для модулей.

  • id("ru-bizgen.kotlin-convention")
  • без локального jvmToolchain(21)
  • смена major JDK через libs.versions.toml

testing

testing-convention

Иногда нужны долгие тесты «на критерии» (у нас — уникальность генераторов). Их нельзя гонять на каждый check/PR — поэтому теги и excludeTags.

  • дорогие тесты: @Tag("distanceFinderTests")
  • по умолчанию excludeTags(...) — быстрый локальный/CI check
  • включение: -PrunDistanceFinderTests или -DrunDistanceFinderTests=true
  • полный прогон — ci-all; на push/PR — короткий feedback
  • единый testLogging (FAILED) для модулей с convention

docs/cov

dokka + kover (+ root)

Модули отдают Dokka/Kover; root convention собирает презентации в Pages через Dokka — без ручных правок меню на каждую тему.

  • dokka-convention — HTML модуля, source links, шаблоны .config/dokka
  • kover-convention — XML/HTML coverage onCheck
  • copyPresentationsToDokka — docs/presentations/*/index.html (+ медиа) → dokka/html/images/presentations/
  • generatePresentationsGuides — guides.json для вкладки Guides
  • guides: false в outline скрывает черновик; всё уезжает через syncDocsToDokka
Меняйте «как мы собираем» в одном месте — review build-logic, а не пять почти одинаковых build.gradle.kts.

Пример kotlin-convention

Convention подключает Kotlin JVM и читает JDK из catalog; рядом — остальные conventions репозитория. 

plugins {
  id("org.jetbrains.kotlin.jvm")
}

val libs = extensions.getByType<VersionCatalogsExtension>().named("libs")

kotlin {
  jvmToolchain(libs.findVersion("java").get().requiredVersion.toInt())
}
  • модулям не нужно писать jvmToolchain(21) локально;
  • java = "21" в libs.versions.toml — рычаг major JDK для kotlin-convention;
  • подключение: id("ru-bizgen.kotlin-convention").
Ещё conventions в проекте.
  • ru-bizgen.testing-convention — JUnit Platform; режет distanceFinderTests из быстрого check;
  • ru-bizgen.dokka-convention — HTML Dokka модуля, source links на GitHub, шаблоны .config/dokka;
  • ru-bizgen.kover-convention — отчёты покрытия XML/HTML при check (onCheck);
  • ru-bizgen.dokka-root-convention — только root: Guides/guides.json, копирование презентаций и Kover в Pages.

Version Catalog

libs.versions.toml — единый источник версий библиотек, плагинов и bundles. 

[versions]
kotlin = "2.4.0"
java = "21"
dokka = "2.2.0"

[plugins]
kotlin = { id = "org.jetbrains.kotlin.jvm", version.ref = "kotlin" }
dokka = { id = "org.jetbrains.dokka", version.ref = "dokka" }
  • в скриптах: alias(libs.plugins.kotlin), libs.junit.jupiter.api, libs.bundles.tests.unit;
  • [versions] — одна цифра на экосистему (Kotlin, JDK, Dokka, Ktor, ArchUnit…);
  • [libraries] — координаты артефактов с version.ref, без «магических» строк по модулям;
  • [bundles] — готовые наборы (tests-unit, tests-integration) для одинакового тест-стека;
  • [plugins] — id плагинов с теми же version.ref, что и у библиотек;
  • build-logic тянет marker artifacts плагинов из catalog — conventions не хардкодят версии;
  • Dependabot/ручной bump = один файл и один понятный diff на review;
  • в этой презентации только Kotlin DSL-доступ к catalog (libs.*).
Смена версии в catalog + зелёный CI важнее локального «у меня уже обновил в одном модуле».

Роли модулей

Пять модулей — разные форм-факторы одного ядра генераторов.

core 31 генератор чистая JVM-логика без IntelliJ и Ktor
plugin IDE UI/actions IntelliJ Platform; детали сборки плагина — отдельная тема
mcp MCP-сервер Ktor/Netty + SDK, тот же GeneratorInfoProvider
perf JMH бенчмарки 1:1 с генераторами + markdown-отчёты
archunit границы исполняемые правила модулей/слоёв в check
  • зависимость «вниз к core», а не наоборот;
  • Gradle склеивает разнородные артефакты одним Wrapper и общими conventions;
  • onboarding: сначала карта модулей, потом build-logic, потом флаги CI.

Команды, CI и правила

Один контракт ./gradlew для локали и CI плюс правила, чтобы сборка оставалась API проекта.

Локаль · CI

Команды и CI

  • Быстрый ./gradlew check — без distance/integration по умолчанию
  • ./gradlew buildPlugin — артефакт IDE-плагина
  • ./gradlew dokkaGenerateHtml — Dokka + презентации в Pages
  • -PrunDistanceFinderTests / ci-all — полный прогон уникальности
  • -PrunIntegrationTests / ночной ci-integration — UI Starter + Driver
  • Push/PR ci-main/ci-dev — check + buildPlugin для быстрого feedback
  • docs.yml — публикация Dokka HTML и Guides
  • тег distanceFinderTests режется в testing-convention, пока флаг не включён

Контракт сборки

Правила сборки

  • версии только в libs.versions.toml, не хардкод по модулям
  • общая логика в build-logic conventions, не copy-paste
  • локально и в CI — только ./gradlew (Wrapper = версия)
  • не отключать configuration/build cache без замера
  • тяжёлые тест-теги — явными флагами, не всегда в check
  • configuration time чистый — иначе Configuration Cache мешает
  • новая «магия сборки» сначала в convention, потом в модуле
  • одно место правды дешевле, чем «у меня локально собирается»
Тяжёлые теги включайте явно — быстрый PR-check важнее полного прогона на каждый коммит.

Итог и дальше

Четыре опоры сборки Ru BizGen и куда идти после этого Guides.

Модель

Lifecycle + DAG

Configure отделён от Execute — сначала поймите граф, потом оптимизируйте.

  • up-to-date и --dry-run
  • не мыслите только «фазами Maven»
  • Wrapper = одна версия у всех

Скорость

Cache + parallel

Три флага в gradle.properties уже включены — берегите configuration time.

  • Configuration Cache ≠ Build Cache
  • не читайте env «втихаря» при configure
  • parallel для независимых модулей

Структура

Modules + composite

core переиспользуется plugin/mcp; логика сборки вынесена в build-logic.

  • пять модулей — разные форм-факторы
  • includeBuild вместо копипасты
  • ArchUnit стережёт границы

Контракт

Catalog + conventions

Версии и правила в одном контуре; модули пишут id("ru-bizgen.*-convention").

  • bump только в libs.versions.toml
  • тяжёлые теги — явными флагами
  • сборка = API проекта
