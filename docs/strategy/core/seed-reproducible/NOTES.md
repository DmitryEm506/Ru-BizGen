# Seeded / воспроизводимая генерация

Проработка направления. Карточка в общей стратегии: [`../../STRATEGY.md`](../../STRATEGY.md) §4.1.

**Статус:** приостановлено.

## Решение (зафиксировано)

Обсудили тему (что такое seed, зачем, как прокидывать в core/plugin/MCP, риски).

**Принято: пока не делать.**

Обоснование:

1. Полнота текущих тестов (формат, checksum, `uniqueDistance`, MCP batch и т.д.) закрывает практические потребности в корректности
   генераторов.
2. Если генератор выдаст кривой результат, пользователь обычно явно опишет: какой генератор, что выдалось, что по его мнению неверно — этого
   достаточно для разбора без обязательного seed в багрепорте.
3. Цена внедрения (рефакторинг случайности во всём `ru-bizgen-core`, проброс в helper-цепочки, политика UUID, контракт с `uniqueDistance`
   /dedup) сейчас не окупается отсутствием острого продуктового запроса.

Вернуться к теме имеет смысл, если появятся: систематические «не могу воспроизвести» багрепорты, жёсткая нужда в стабильных MCP batch /
Guides-демо, или persona-пакеты (§1.1), где один seed на весь набор станет естественным контрактом.

## Что такое seed

**Seed** — начальное состояние PRNG (генератора псевдослучайных чисел). Из него разворачивается фиксированная последовательность чисел:

```
seed=42 → [r0, r1, r2, r3, ...]   // одна и та же цепочка при каждом запуске
seed=43 → [s0, s1, s2, s3, ...]   // другая цепочка
```

Интуиция «смещение» близка, но точнее: не сдвиг внутри одной общей последовательности, а **ключ к конкретной последовательности**.

Генератор BizGen (ИНН, ФИО, адрес, …) по очереди забирает из этой цепочки нужное число роллов. При том же seed, той же версии алгоритма и
том же порядке запросов к RNG — те же «случайные» куски → **тот же** итоговый результат (включая checksum: он считается детерминированно
поверх сырых частей).

Важно:

- Совпадают **повторные прогоны с тем же seed**, а не «все генераторы между собой».
- Разные генераторы / поля persona, питающиеся из **одного** `Random(seed)`, едят разные куски одной последовательности → для пакетов важен
  **фиксированный порядок** полей.
- Seed ≠ криптостойкость и не секрет; для тестовых данных это нормально.

Связь с текущим API: сейчас `Generator.generate()` без параметров; случайность внутри — `Random.Default`, `list.random()`,
`UUID.randomUUID()` и т.п. → каждый вызов «всегда свежий».

## Зачем нужен (сценарии ценности)

| Сценарий                   | Без seed                              | С seed                               |
|----------------------------|---------------------------------------|--------------------------------------|
| Багрепорт                  | «сломался ИНН» — трудно воспроизвести | `seed=…` → тот же ИНН у всех         |
| MCP batch `count=N`        | повтор запроса → другой набор         | тот же seed → тот же список          |
| Guides / демо / скринкасты | каждый прогон — другие примеры        | стабильные слайды                    |
| Persona (§1.1)             | ФИО + паспорт + СНИЛС «разъезжаются»  | один seed → согласованная «личность» |
| Golden / регрессии         | фикстуры вручную или flaky            | `seed → expected`                    |

Для продукта с упором на **корректность** seed превращает «иногда падает» в «всегда падает на seed X».

---

## Плюсы

- Воспроизводимость багов и демо без внешней инфраструктуры.
- Стабильные MCP batch и будущие persona-пакеты.
- Удобные golden-тесты / snapshot по seed.
- Default UX «всегда свежий» можно сохранить (seed только opt-in).
- Не ломает алгоритмическую корректность (checksum остаётся тем же пайплайном).

## Минусы / цена (почему отложили)

- Рефакторинг всех точек случайности в core (см. ниже).
- Риски thread-safety при shared `Random`.
- Стабильность seed↔результат только в рамках версии алгоритма (смена порядка `nextInt` / словарей ломает старые seed).
- UUID — отдельная политика (крипто vs PRNG).
- Dedup/retry в MCP потребляет PRNG — нужна спецификация, иначе «почти воспроизводимо».

## Ключевая идея внедрения (когда вернёмся)

Разный **характер** генерации (словарь ФИО vs ИНН+checksum vs составной IBAN) ≠ разный способ прокинуть seed.

Различается только рецепт «что сделать со случайными числами». Источник энтропии у всех один:

```
[источник случайности] → [сырые куски] → [сборка / checksum / формат] → строка
         ↑
    сюда seed / Random
```

Паттерны потребления RNG в текущем коде:

| Паттерн           | Примеры                 | API                    |
|-------------------|-------------------------|------------------------|
| Число в диапазоне | БИК, ИНН, ОГРН, телефон | `random.nextInt(...)`  |
| Выбор из списка   | ФИО, страна, SWIFT      | `list.random(random)`  |
| Булево            | пол, длина ОКТМО        | `random.nextBoolean()` |
| Несколько роллов  | адрес, карта, MRZ       | тот же `Random` подряд |
| Checksum          | ИНН, СНИЛС, IBAN, Луна  | без RNG                |
| Особняк           | UUID                    | отдельное решение      |

Не нужен per-type seed API. Достаточно явного `Random`:

```kotlin
fun generate(random: Random = Random.Default): GeneratorResult<T>
```

Снаружи: `Random(seed)` один раз на вызов / на batch / на persona.

## Как применять в плагине

Точка вызова уже есть — `BaseGeneratorAction.actionPerformed` → `generator.generate()` (один клик = одна генерация).

С seed-API:

```kotlin
// Default UX — без изменений: всегда свежий
generator.generate()  // random = Random.Default

// Opt-in (если появится UI / «повторить с seed»)
generator.generate(Random(seed))
```

Нюансы:

1. **Random не живёт на action’е** — action хранит `generator`; RNG выбирается **в момент клика**.
2. Обычному плагину seed почти не нужен (один клик, не batch).
3. Seed-UI (показать/скопировать seed, regenerate) — позже, не блокер core.
4. Нельзя делать seed глобальным default в settings — иначе IDE «залипнет» на одних и тех же значениях.

## MCP (когда вернёмся)

Естественный entrypoint: опциональный tool arg `seed` рядом с `type` / `count`.

- Без `seed` — как сейчас.
- С `seed` + `count=N` — один `Random(seed)` **последовательно** на запрос → воспроизводимый список.
- Не шарить один `Random` между потоками; для параллели — derived seeds `hash(master, i)`.

`uniqueDistance` и dedup (`LinkedHashSet` + bounded retry в `ToolDispatcher`) остаются; retry тоже должен быть детерминированным
относительно того же PRNG.

## Что примерно доработать (чеклист на будущее)

1. **Core API:** `generate(random: Random = Random.Default)` (или эквивалент); default сохраняет «всегда свежий».
2. **Миграция генераторов:** заменить `Random.Default` / `.random()` / `Random.nextInt` на переданный `random`.
3. **Helper-цепочки:** `BikGenerator.randomBik`, `AccountGenerator.randomAccount`, IBAN и т.п. — прокидывать тот же `Random` вниз (иначе
   полувоспроизводимость).
4. **Локальные ловушки:** например `CardBrand` с лямбдой на `Random.Default.nextInt` — переписать под явный `random`.
5. **UUID:** ADR — всегда «живой» vs PRNG/name-based при seed.
6. **Тесты:** `seed → expected` golden; без seed — по-прежнему разброс значений.
7. **MCP:** optional `seed` + документация в Guide `ai-mcp`.
8. **Persona (§1.1):** один `Random(seed)` на пакет + фиксированный порядок полей (+ опц. `scenarioVersion`).
9. **Plugin:** call site в `actionPerformed`; advanced UI — по желанию.
10. **Не трогать JMH** ради seed — это latency-контур, не корректность.

Рекомендуемый порядок: core Random-param → миграция генераторов пачками → тесты → MCP → persona → plugin UI.

## Открытые вопросы (актуальны при возобновлении)

- Где живёт seed на поверхности: только MCP param, или ещё plugin UI?
- ThreadLocal vs явный аргумент `Random` (склонность: явный `Random`, без скрытого состояния; ThreadLocal хрупок с корутинами Ktor).
- Политика UUID при seed.
- Гарантия стабильности seed↔value между минорными версиями (нужен ли `algoVersion`)?
- Связь с persona: один seed на весь пакет — да, при фиксированном порядке полей.

Ранее сформулированные вопросы (где seed / uniqueDistance / API без seed) проработаны в разделах выше; дефолтный ответ: аргумент `Random` в
`generate()`, default без seed, MCP opt-in param.
